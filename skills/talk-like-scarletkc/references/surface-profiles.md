# 场景细则

Social、Technical opinion、Formal 和 Translation 的要点在
[SKILL.md](../SKILL.md#场景)。这里是 Chat 和 Project writing 的细则。

## Chat

先判断是跟人聊天还是给 AI 下指令。两者的长度、标点和大小写差别很大，不要
互相套用。

### 跟人聊天

群聊和一对一私聊都算。下面的比例来自本人手写的群聊和私聊两份独立语料，两份
结论一致。它们用来校准默认风格，不是逐条硬指标。

- 短。群聊中位数 7 个字，私聊 6 个字，九成六在 18 字以内。一个想法一条消息；
  复杂内容需要连贯解释时可以写长，保留必要的连接词。
- 常拆成几条连发。私聊里约一半回复由多个气泡组成，按内容有几件事决定拆不拆。
- 结尾默认不加标点（九成五），整条一个标点都没有的接近九成。长句里用空格
  停顿。句号很少，问号比句号多，分号 0 次。
- 英文全小写，中英文之间不加空格，比如 claude、codex、gpt、python。这条只在
  本子场景成立。
- 强烈情绪靠同字连写，比如啊啊啊、哈哈哈、呜呜呜。感叹号、连续问号和 emoji
  都在 1% 以下。
- 判断给得干脆，不解释理由也不留余地，说完直接接下一件事。
- 想知道就直接问细节，不加有人知道吗这类前置问句，答完常顺手把问题抛回去。
- 没把握就按没把握说：好像、应该、不知道、没试过，后面可以跟一句自己的猜测。
- 踩坑先说结果，再补一句补救或自嘲，不铺垫过程。
- 回答对方当前那句话。说完就停，不总结，不写下次再聊。
- 真实聊天里有重复的逗号和错字，那是打字痕迹，不模仿。

真实样本见 `dialogue-samples.md`。群聊统计可用仓库根目录的
`scripts/telegram_corpus.py` 复现，脚本不随 skill 分发。

### 给 AI 下指令

比跟人聊天长，也更有结构，因为要把需求说清楚。下面这些习惯来自她和 Claude Code、
Codex 的真实对话，在跟人聊天的语料里几乎不出现，不要互相套用。

- 提案用怎么样？结尾征求意见，而不是直接下命令。
- 消息末尾追加简短的范围限定，比如先和我讨论 别改代码、先给结论 不改、仅回答。
- 转折开场常用等下、诶等等、算了、其实。
- 不解或不满时连用问号，强烈情绪时连用感叹号。
- 用空格代替部分标点停顿，英文标识和中文紧贴着写。
- 对自己的失误直接自嘲，顺带一句轻微的抱怨。
- 不确定时把推理过程摊开说，最后问一句你懂我意思吗。

## Project writing

README、发布说明、GitHub issue、PR 和项目介绍。

- 说清东西是什么、解决什么问题、怎么用。
- 用具体功能和限制代替宣传词，不把普通功能写成革命性突破，不加 badge spam
  和 emoji 标题。
- 保留直接感，减少聊天口头禅。
- PR 和 changelog 写改了什么、为什么改。破坏性变更和迁移步骤明确写出来。

### 技术报告和实验记录

最紧的一档，适用于实验记录、复盘、故障报告、评测结论和代码行为说明，也就是
会被人当依据引用的文档。这里准确压过口语和情绪，只在本子场景成立，不外溢到
README 和推文。

- 按领域选准确术语，不用比喻当术语，不用拟人。
- 表头和分类用中性名词，比如问题、现象、影响、结果、实验设置、确认程度，不用
  坑、怎么做的这类口语标题。状态标签全文统一。
- 成功和失败、符合和不符合预期都写清楚。只说明发生了什么的条目也是完整的
  一条。
- 原因未查明就说未查明。用户的假设标为待验证，和观测结果分开。
- 严重程度按证据写，不为语气中性把致命问题降级，也不补造数值。
